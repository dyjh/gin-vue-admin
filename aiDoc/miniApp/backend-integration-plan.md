# 后端实现与联调计划

## 目标

在不重新设计前端页面的前提下，依据 `api.json` 实现 Go 后端，将 `miniApp/` 从本地 Mock 平滑切换到真实接口，并同步建设与业务状态一致的 gin-vue-admin 后台 Web。

本阶段以“接口可用、数据可靠、状态闭环、关键规则有测试”为完成标准，不扩展第一版范围。

## 实施顺序

### -2. 微信身份、能力策略与发布包命名冻结

- 冻结冷启动 `wx.login -> code -> openid -> 业务令牌` 流程。
- 登录接口不接受客户端提交 `openid`，也不向客户端返回 `openid`、`unionid` 或 `session_key`。
- 冻结平台默认关闭、用户“跟随平台/开启/关闭”三态覆盖和全局紧急停用优先级。
- 冻结增强能力关闭时积分、积分流水、打卡奖励和偏好分析同步关闭的规则。
- 将小程序接口模块、ID、路径、模型和字段改为中性命名。
- 盘点并迁移 `pages/ai/`、`prep-ai.*`、变量、文案、Mock、资源名和远程资源 URL。
- 在 `miniApp/` 之外建立实际上传包扫描脚本，结果为 0 才允许发布。

### -1. 契约冻结与 GVA 基线

- 校验 `api.json` 可以解析，所有模型和枚举引用都有定义。
- 校验小程序接口契约中不再包含 AI 相关模块、路径、模型和字段名。
- 冻结菜品 `draft|usable`、饭局 `collecting|closed|confirmed|cancelled` 和软删除口径。
- 冻结小程序公开 ID、统一时间格式、分页、错误码和幂等头。
- 使用 `mcp:order_food_mini_app` 保存当前 API、菜单和 package 基线。
- 通过 `gva_analyze` 确认 `orderfood` package 生成范围。
- 只对分类、标签、单位等稳定 CRUD 使用 `gva_execute`；生成后执行 `gva_review`。
- 明确后台根菜单、组件路径、角色、按钮权限和 API 权限，禁止自动生成与手工注册重复。

### 0. 工程与公共能力

- 建立 `server/model|service|api/v1|router/orderfood` 业务包和 `enter.go` 聚合入口。
- 建立小程序 API 路由组和统一响应封装。
- 建立后台 `/api/orderfood` 路由组和 GVA 管理员权限边界。
- 接入请求追踪 ID、鉴权中间件、参数校验和统一错误码。
- 建立数据库迁移、测试数据与本地开发配置。
- 建立平台能力策略、用户覆盖、动态文案、配置版本和审计表。
- 建立统一 `capability` Service 和受控业务门禁。
- 明确对象存储、微信登录、阿里云图片审核和 AI 服务商的环境变量。
- 建立 `web/src/api/orderfood/` 与 `web/src/view/orderFood/`。

### 1. 登录、用户与上传

- 实现 `system`、`auth`、`profile`、`upload`。
- 小程序 `App.onLaunch` 自动调用 `wx.login`，所有页面请求等待同一认证 Promise。
- 后端调用 `jscode2session`，按唯一 `openid` 查找或创建用户，签发访问令牌并返回 `RuntimeConfig`。
- 打通访问令牌、头像昵称、用户禁用状态、平台策略和用户三态覆盖。
- 后台完成平台默认状态、全局紧急停用、动态文案和用户覆盖配置。
- 图片先上传并同步完成内容审核，审核不通过时不创建业务对象。
- 保存图片资源与审核记录，允许业务对象在后续保存时绑定资源 ID。
- 后台完成小程序用户列表、用户详情、禁用/恢复、图片资源和图片审核记录页面。

### 2. 菜品、菜谱与推荐

- 实现 `dish`、`recipe`、`recommendation`。
- 菜品封面必选、简介选填，做法步骤支持纯文字或文字加大图。
- 推荐复制进入个人菜品库后默认未公开，并永久禁止再次设置为允许被发现。
- 菜谱只引用个人菜品；菜品删除、菜谱移除和推荐复制需覆盖边界测试。
- 后台完成分类、标签、单位、可发现候选池、推荐精选和官方菜品。
- 可发现候选池不建立额外审核状态；精选进入推荐即为平台内容把关。

### 3. 积分、增强能力与打卡

- 实现小程序 `points`、`assist`、`checkin`，后端内部 AI 领域负责供应商和模型调用。
- 小程序调用层使用中性 `assist`、`mealSuggestion`、`prepPlan`、`featureUsage` 命名；后端内部仍可使用 AI 领域术语。
- 每个受控接口在 Service 层校验当前用户有效能力状态。
- 有效状态关闭时，积分接口不可用；打卡成功但奖励为 0，不写奖励流水、不触发偏好分析。
- 历史积分和流水只隐藏，不清零、不删除。
- AI 请求使用 `requestId` 和数据库事务保证扣分幂等。
- 模型失败或超时后必须落积分退款流水，并产生对应站内通知。
- “不知道吃什么”先执行 SQL 硬条件过滤和推荐池召回，样本不足时才调用 AI。
- 打卡图片分析异步更新用户偏好画像，不阻塞打卡主流程。
- 后台完成积分流水与调整、AI 供应商、模型、能力配置和调用记录。
- 后台能通过请求 ID 串联 AI 调用、扣分、退款和通知。

### 4. 饭局与采购清单

- 实现 `meal`、`shopping`。
- 候选菜阶段只保存稳定候选项引用；确认最终菜单后才生成完整饭局菜品快照。
- 点餐码、截止时间、提前关闭、最终份数和饭局状态流转必须由后端校验。
- 采购清单不分类，支持待购买、已购买、新增、编辑、删除、复制与只读分享。
- 分享令牌只授予查看权限，不能修改原采购清单。
- 后台完成饭局、点选统计、最终快照和采购清单的只读诊断页面。
- 后台不提供修改点选、份数、截止时间和饭局状态的越权入口。

### 5. 通知与端到端联调

- 实现 `notification`，接入站内通知分页、未读数和全部已读。
- 列表接口默认每页 20 条，前端无限滚动并按 ID 去重。
- 微信订阅消息只在用户授权对应模板后发送，站内通知始终保留。
- 完成菜品录入、推荐复制、菜谱、饭局点菜、确认菜单、采购、打卡、积分和通知的端到端验收。
- 后台完成内容治理、站内通知、订阅消息模板与发送记录。
- 最后补运营概览，指标只使用已经稳定的业务数据。

## Mock 退出策略

不建议一次性关闭全部 Mock。每完成一个模块后按以下顺序切换：

1. 后端接口、迁移和单元测试完成。
2. 对照 `api.json` 运行契约测试。
3. 小程序请求层接入真实接口，并保留模块级回退开关。
4. 微信开发者工具验证加载、空状态、错误状态和分页。
5. 真机验证登录、上传、分享、授权和安全区。
6. 该模块稳定后移除对应 Mock 路由与测试数据依赖。

小程序相关模块切换真实接口前，还必须完成页面路径、文件名、变量、静态文案、接口路径和资源 URL 的中性化迁移。不能只把按钮隐藏后继续上传含敏感命名的包。

若当前全局 `useMock` 无法支持逐模块切换，应先改造成模块级配置，避免联调期间所有页面同时失效。

## 每个模块的完成标准

- 数据模型、迁移、服务、API、路由和权限注册完整。
- 请求与响应符合 `api.json`，错误码稳定。
- 写操作具备权限校验；关键写操作具备幂等或冲突保护。
- 正常、空数据、无权限、状态冲突和依赖失败均有测试。
- 前端不再依赖该模块的 Mock 数据。
- 对应后台页面具备加载、空、错误、无权限和状态冲突表现。
- 后台菜单、按钮和 API 权限经过最小权限验证。
- 微信开发者工具和至少一台真机验证通过。
- 实际微信上传包敏感字样和敏感路径扫描为 0。

## 必测业务规则

- AI 扣分与退款在并发和重试下只执行一次。
- 冷启动只执行一次微信 `code` 兑换，并发首次登录只创建一个用户。
- 平台默认、用户三态覆盖和全局紧急停用优先级正确。
- 关闭状态下受控接口拒绝执行，积分隐藏，打卡零奖励且不投递偏好分析任务。
- 能力策略配置版本变化后，小程序旧缓存失效。
- 上传审核失败时不调用 AI、不扣分、不创建业务数据。
- 推荐复制品不能重新公开，源菜品普通下架不级联删除复制品。
- 用户删除菜品时删除其图片资源；历史饭局保留文字快照但不依赖已删除图片。
- 饭局确认前不生成完整快照，确认后历史数据不受菜品编辑影响。
- 采购分享页只读，分享令牌无效或过期时返回明确错误。
- 通知分页顺序稳定，全部已读不删除历史记录。
